# 移动端页面加载性能诊断报告

> 诊断日期：2026-09-09
> 诊断方式：源码审计 + 真实数据库实测（复制数据副本到临时 MySQL 8.0 容器，原始 `data/mysql` 未做任何改动）
> 结论一句话：**确实每次都查库，而且比"查库"本身更严重——是每次都对 5.6 万行的题目表做全表扫描并实例化成 Java 对象。**

---

## 一、实测数据（真实库）

复现环境：本地 Windows 宿主机 + MySQL 8.0 容器（**本机性能远好于生产 ECS 2 核 4G，生产环境经验上要乘 2~4 倍**）。

### 1.1 数据规模

| 表 | 行数 | 说明 |
|---|---:|---|
| `practice_question` | **56,400** | 基础题库，且 **全部** `status=1 AND admin_audit_status=2`（过滤条件几乎不减少扫描量） |
| `sp_case_config` | 6,082 | 病例库（公开 6,074） |
| `student_practice_record` | 71 | 学生答题记录（目前少） |
| `practice_question` 单行文本量 | 201 字节 | 全表文本约 **10.8 MB**（title + options_json + answer + explanation） |

### 1.2 SQL 实测耗时（热缓存）

| 场景 | 对应接口 | 耗时 |
|---|---|---:|
| `GROUP BY department` | `/questions/departments` | **126 ms** |
| `GROUP BY knowledge_tag` | `/questions/knowledge-tags` | **142 ms** |
| 分页 `LIMIT 20`（三字段排序） | `/questions` 第 1 页 | **106 ms** |
| 分页 `LIMIT 2000,20` | `/questions` 深翻页 | **94 ms** |
| 全表 `GROUP BY knowledge_tag` | `/questions/stats` 内部第 1 次 | **108 ms** |
| 全表 `GROUP BY department` | `/questions/stats` 内部第 2 次 | **90 ms** |
| 病例广场科室 | `/case-market/departments` | 1 ms（表小，没问题） |

> ⚠️ 注意：上表是 **SQL 层** 耗时。真正的重灾区在 **ORM 层**——见 3.3，Java 侧开销比 SQL 大一个数量级。

## 二、根因总览

| # | 根因 | 影响面 | 严重度 |
|---|---|---|---|
| A | **无缓存**：全后端仅 4 个类用了 Redis（每日病历、在线统计、验证码），题库/统计/纠错类接口一个都没有 | 全局 | 🔴 高 |
| B | **`stats()` 两次全表捞进内存**：56,400 行 × 2 次被 `selectList` 实例化成 Java 对象 | 成长页 | 🔴 极高 |
| C | **N+1 查询**：按 `answeredIds` 逐条 `selectById` | 成长页 | 🟠 中（随使用增长） |
| D | **科室/知识点列表无缓存**：每次开页面都全表 `GROUP BY` | 题库页 ×2 | 🟠 中 |
| E | **页面级 loading 阻塞**：`AmbientScaffold.loading=true` 时整块内容区被骨架屏替换，必须等全部接口返回 | 学生端多页 | 🟠 中 |
| F | **首屏自动补拉**：内容不足一屏时立即串行补拉下一页 | 题库页 | 🟡 低 |
| G | **移动端零缓存**：每个页面 `initState` 都重新请求，切页/返回即重拉 | 全局 | 🟠 中 |

## 三、逐页面根因分析（学生端）

### 3.1 基础题库页 `question_training_screen.dart`

```dart
void initState() {
  WidgetsBinding.instance.addPostFrameCallback((_) => _load());  // 每次进页面都拉
}
_load() => StudentService().getQuestionDepartments();             // 126ms 全表 GROUP BY
```

- 页面 `loading: _isLoading`，一个科室列表接口没回来之前整页骨架屏。
- 科室列表**几乎不变**（只会随题库导入变），却每次进页面都重查。

### 3.2 浏览题库页 `question_bank_screen.dart`

`initState` 里两个并发：

```dart
_loadFirst();   // GET /questions  → 106ms + MyBatis-Plus 额外 COUNT(*) 全表统计
_loadFilters(); // departments(126ms) + knowledge-tags(142ms) 两个全表 GROUP BY
```

- 首屏实际是 **3 个重查询并发 + 1 次 COUNT 全表扫描**。
- 更糟的是 `_loadFirst()` 尾部：首屏不足一屏时 `addPostFrameCallback` 再补拉一页（**+106ms 串行**）。
- 翻页时 MyBatis-Plus 每次都要跑一遍 `SELECT COUNT(*)`（5.6 万行）。

### 3.3 🔴 成长页 `growth_screen.dart`（最严重）

```dart
final results = await Future.wait([
  StudentService().getReportOverview(),                    // 轻
  StudentService().getMistakes(pageNum: 1, pageSize: 50),  // 轻（批量查，写得不错）
  StudentService().getQuestionStats(),                     // 🔴 重灾
]);
// loading: !_statsReady → 三个全回来才渲染（木桶效应）
```

`getQuestionStats()` → `PracticeQuestionServiceImpl.stats()` 的问题：

```java
// ① 两次全表捞进内存（不是 SQL 聚合，是 selectList 全量实体）
private void practiceTagCounts(...)  { questionMapper.selectList(...); }  // 56,400 个对象
private void practiceDeptCounts(...) { questionMapper.selectList(...); }  // 再来 56,400 个对象

// ② N+1：逐条 selectById
Map<Long, PracticeQuestion> qCache = new HashMap<>();
for (Long qid : answeredIds) {
    PracticeQuestion q = qCache.computeIfAbsent(qid, questionMapper::selectById);  // 每条一次 SQL
}
```

**量化影响**：

| 项 | 数值 |
|---|---|
| SQL 耗时 | 108 + 90 = ~198 ms |
| ORM 实例化对象 | 56,400 × 2 = **112,800 个 `PracticeQuestion` 实体** |
| 堆内存分配（估算） | 文本 10.8 MB × 2 次 + 对象头开销 → **约 60~100 MB 临时垃圾 / 每次调用** |
| N+1 次数 | 当前学生 33 次（会随刷题量线性增长） |

生产 ECS 是 **2 核 4G**，JVM 堆可能只有 1G 左右——每次打开成长页瞬时分配近 100MB 垃圾，必然触发 Full GC，**这就是"半天才出来"的直接原因**。而且这是 GC 停顿，所以表现为"有的时候特别慢"（GC 时机不确定）。

## 五、为什么是"有的时候"才慢？

四个因素叠加：

1. **MySQL Buffer Pool 冷热**：长时间没访问 → 数据页被淘汰 → 走磁盘 IO，慢几倍。
2. **GC 时机随机**：`stats()` 每次分配 ~100MB 垃圾，是否撞上 Full GC 决定这次快不快。
3. **生产资源争抢**：ECS 2 核 4G 上挤了 MySQL + Redis + 后端 + AI + Nginx + Milvus/etcd，CPU 抖动直接放大所有接口耗时。
4. **网络**：真机走局域网/公网，每次请求额外 RTT；成长页 3 个并发 + 题库页 3~4 个并发。

## 六、修复方案（三档，请拍板）

### P0 — 后端改造，改动小收益最大

| 项 | 改法 | 预期收益 |
|---|---|---|
| **B1** `stats()` 两次全表 | `selectList` 全量捞 → 改 `selectMaps` 聚合：`SELECT knowledge_tag, COUNT(*) ... GROUP BY knowledge_tag`（只返回几十行）。两次合并成一次或保持两次但都走聚合 | 内存 100MB → **<1MB**，耗时降一个数量级 |
| **B2** N+1 | `for + selectById` → 一次 `selectList(where id in (...))` 批量查 | 33 次 SQL → 1 次 |
| **B3** 科室/知识点 | 加 Redis 缓存（`@Cacheable`，TTL 10~30 分钟）或 Caffeine 本地缓存 | 126/142ms → **~0ms** |
| **B4** 索引 | 新增联合索引 `(status, admin_audit_status, department)`、`(status, admin_audit_status, knowledge_tag)` | GROUP BY 走覆盖索引，免全表 |

> B1+B2 是**纯赚无副作用**的改动，强烈建议优先做。

### P1 — 移动端体验优化

| 项 | 改法 |
|---|---|
| **M1** 页面级内存缓存 | 成长页/题库页数据缓存 30~60 秒（Riverpod provider + TTL），二次进入秒开 |
| **M2** 分步渲染 | 成长页不必等三个接口全回：先渲染花园/热力图，统计数字后到（消除木桶效应） |
| **M3** 题库首屏 | 首屏 pageSize 20 → 40，或去掉"不足一屏立即补拉"，改滚动时再拉 |
| **M4** 科室列表持久化 | 科室/知识点存 SharedPreferences，启动即用，后台静默更新 |

### P2 — 架构层面

| 项 | 改法 |
|---|---|
| **S1** 教师工作台 | overview 串行 9 步 → 并发 + 结果缓存（按 teacherId+classId，TTL 1~5 分钟） |
| **S2** 全局缓存层 | 引入 Caffeine/Redis 统一缓存注解，覆盖"低频变动"的统计类接口 |
| **S3** 分页 COUNT 优化 | MyBatis-Plus 分页插件配置 `countSql` 优化 / 总数缓存，避免每次翻页全表 COUNT |
