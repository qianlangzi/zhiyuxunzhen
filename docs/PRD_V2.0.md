| 术语 | 释义 |
| --- | --- |

| RBAC | Role-Based Access Control，基于角色的访问控制，用于限制不同身份可访问的功能和数据范围。 |
| SLO | Service Level Objective，服务等级目标，用于约束性能、可用性、错误率等生产运行指标。 |
| 灰度发布 | 将新版本先开放给少量用户或指定班级，验证稳定后逐步扩大范围的发布策略。 |
| RTO / RPO | 容灾恢复指标。RTO 表示服务恢复时间目标，RPO 表示可接受的数据丢失时间窗口。 |

## 一、项目背景与产品目标

### 1.1 背景与机会

高校临床医学教育正在从“知识讲授”转向“能力训练”。内科学是临床医学的主干课程，覆盖疾病谱广、诊断链条长、鉴别诊断复杂，是学生从基础医学走向临床实战时最容易出现断层的学科。

当前教学现场存在三个突出矛盾：

- **学生练习机会不足**：真人 SP 培训和组织成本高，学生很难高频、低压力地练习问诊、鉴别诊断和临床沟通。
- **教师批阅负担过重**：大病历批改耗时长，教师通常需要逐份阅读、标注逻辑漏洞、纠正错漏字，难以兼顾临床工作和教学质量。
- **教学管理缺少数据闭环**：教研室知道学生“考得不好”，但很难定位到“哪类疾病、哪一步问诊、哪个检查决策”持续薄弱。

大模型、多模态识别、RAG 知识库和智能体编排技术已经具备将“虚拟病人训练、临床思维评估、作业批阅、学情分析”打通的条件。本项目目标是把 AI 从简单问答工具升级为面向内科学建设的教研协同平台。

### 1.2 产品定位

智愈寻真是面向高校一流内科学建设的“教-学-管”三位一体 AI 训练平台：

- 对学生：提供沉浸式 AI 问诊、影像/检验判读、临床思维可视化、错题复盘和每日训练。
- 对教师：提供零代码病例配置、作业分发、智能批阅、病例共享和班级学情分析。
- 对管理者：提供用户审核、内容质检、模型成本监控、系统降级、审计日志和教学运营总控。

### 1.3 目标用户

| 用户类型 | 用户范围 | 关键诉求 |
| --- | --- | --- |
| 主体用户 | 大三、大四临床医学生 | 理论学习黄金期，需要把教材知识转化为问诊逻辑、诊断路径和病例书写能力。 |
| 辐射用户 | 大二学生 | 需要完成基础医学到临床课程的衔接，适合轻量病例和每日一例。 |
| 辐射用户 | 大五学生 / 规培生 | 需要接近真实临床的 OSCE 训练、影像判读、鉴别诊断和沟通训练。 |
| 教师用户 | 附属医院临床带教主治医师、教学秘书 | 需要快速出题、批阅、复核、查看班级薄弱点和复用优质病例。 |
| 管理用户 | 教研室主任、平台运维工程师、教学督导员 | 需要看全局数据、管用户、管内容、管模型成本、管安全合规。 |

### 1.4 Success Metrics

| 指标类型 | 指标 | 目标值 | 口径 |
| --- | --- | --- | --- |
| 教师效率 | 单份大病历批阅时长 | 缩短 70%，从 15 分钟降至 3 分钟内 | 统计教师从打开批阅页到提交复核的平均时长 |
| AI 体验 | 多模态对话首 Token 延迟 | ≤ 1.5 秒 | 从学生发送消息到首个 SSE token 到达前端 |
| 教学效果 | OSCE 模拟考“问诊逻辑”单项均分 | 提升 ≥ 15% | 对比使用平台前后同类班级或同一班级前后测 |
| 学习活跃 | 每日一例完成率 | 试点班级周均完成率 ≥ 60% | 每周完成 ≥ 4 次每日一例的学生占比 |
| 内容生态 | 病例广场可复用病例数 | 试点期 ≥ 100 个审核通过病例 | 管理员审核通过且至少被引用 1 次 |
| 系统稳定 | 单班级并发 SSE | 50 人无排队 | 同一班级同时开启问诊，系统不拒绝、不白屏 |

### 1.5 上线标准

系统达到以下条件后，才允许进入试点院校生产环境：

- 核心业务链路可用率不低于 99.5%，连续监控 30 天无 P0 故障。
- 关键接口具备超时、重试、降级、告警和审计闭环。
- 所有 P0 功能均完成测试用例、验收用例和回归用例。
- 安全测试覆盖鉴权、越权、上传、注入、敏感信息和审计链路。
- 生产环境支持灰度发布、回滚、备份恢复和容量监控。
- 医学内容通过专家审核流程，病例广场支持下架和追溯。

3. **管理端**：全局驾驶舱、用户权限管理、内容风控与质检、系统运维配置、审计日志与安全。

### 2.2 企业级上线范围

V2.1 以“可生产、可审计、可扩展、可运营”为目标，完整覆盖以下能力：

- 教师端：SP 配置、病例广场、作业分发、格式盾牌、智能批阅、学情看板、内容治理。
- 学生端：多模态 AI 问诊、临床思维决策树、OSCE 雷达图、每日一例、错题本、复盘报告、个性化补救路径。
- 管理端：全局驾驶舱、用户权限管理、教师资质审核、内容质检、模型配置、审计日志、安全合规。
- 系统底座：RAG 知识库、AI 智能体编排、SSE 流式服务、模型降级、监控告警、成本控制、容灾恢复。

### 2.3 非目标范围

- 不面向真实患者提供诊疗建议，不替代临床医师诊疗责任。
- 不替代教师最终评分权，AI 结果仅作为辅助建议与初筛依据。
- 不在首版强制接入医院真实 HIS / LIS / PACS，但预留标准接口和数据模型。
- 不把离线单机演示作为目标，系统以联网企业级部署、持续运维和审计追溯为前提。

### 3.2 核心用户旅程

#### 3.2.1 教师出题与批阅闭环

1. 教师进入助教端，创建 SP 病例或从病例广场引用病例。
2. 教师设置作业标题、班级、截止时间、是否要求大病历、防作弊变量。
3. 学生完成 AI 问诊并提交大病历。
4. 系统先执行格式盾牌校验，不通过则打回学生修改。
5. 校验通过后进入 AI 批阅，生成错误高亮、扣分项、综合评语。
6. 教师查看 AI 批阅结果，进行人工复核和覆盖。
7. 学情看板聚合全班共性薄弱点，辅助下一次课堂讲解。

#### 3.2.2 学生训练与复盘闭环

1. 学生从首页进入作业、每日一例或自主训练病例。
2. 学生与 AI 病人流式对话，可上传影像/检验图片并圈画异常点。
3. 右侧临床思维决策树实时展示已问内容、已排除诊断、遗漏检查和检查成本。
4. 学生提交诊断后，如错误，系统按三级策略进行苏格拉底式引导。
5. 问诊结束后，系统生成 OSCE 四维雷达图和综合评语。
6. 错误诊断、漏问项目、错误检查决策自动进入错题本。
7. 学生可导出 AI 复盘报告，用于考前复习。

#### 3.2.3 管理治理闭环

1. 管理员在全局驾驶舱查看活跃、Token 消耗、待审核病例、异常错误。
2. 教师提交资质认证，管理员审核执业医师证或教学授权材料。
3. 病例广场内容进入管理员终审，通过后展示“官方认证”标识。
4. 管理员维护敏感词、教材版本、每日一题排期、模型降级策略。
5. 敏感操作写入审计日志，支持按人、时间、操作类型追溯。

## 四、功能需求详述

### 4.1 教师端：零代码 SP 配置台

#### 4.1.1 功能目标

让教师通过表单快速创建标准化病人，降低病例制作门槛，并将病例配置结构化沉淀为可复用资产。

#### 4.1.2 功能说明

| 子功能 | 需求说明 | 优先级 |
| --- | --- | --- |
| 基础信息配置 | 支持填写病例标题、适用年级、科室、疾病分类、难度、知识点标签。 | P0 |
| 患者画像配置 | 支持填写年龄、性别、职业、主诉、现病史摘要、既往史、过敏史、家族史。 | P0 |
| 隐藏疾病配置 | 教师配置真实诊断、关键阳性体征、关键阴性体征、误导信息和鉴别诊断。 | P0 |
| 性格与沟通风格 | 支持选择配合、焦虑、暴躁、隐瞒、表达不清、过度担忧等人格标签。 | P1 |
| 检查项目配置 | 预置可开检查、检查结果、费用、是否关键检查、是否过度检查。 | P1 |
| 标准路径配置 | 教师可配置推荐问诊路径、必要检查、诊断依据和扣分点。 | P1 |
| 草稿与发布 | 支持保存草稿、预览试诊、发布至班级或提交病例广场。 | P0 |

#### 4.1.3 关键规则

- 单个病例最多关联 8 个知识点标签。
- 隐藏疾病和标准路径只对教师、管理员、AI 评估节点可见，学生不可见。
- 病例发布后如已被作业引用，核心诊断字段不可直接覆盖，只能创建新版本。
- 教师预览试诊不计入学生训练数据和学情统计。

### 4.2 教师端：病例广场

#### 4.2.1 功能目标

将教师个人病例沉淀为学院共享资产，形成可复用、可评价、可治理的内科教学案例生态。

#### 4.2.2 功能说明

| 子功能 | 需求说明 | 优先级 |
| --- | --- | --- |
| 病例发布 | 教师可将自建病例提交至病例广场，需补充适用年级、疾病系统、难度、教学目标。 | P1 |
| 预览试诊 | 引用前可进入教师预览模式，与 AI 病人试诊并查看标准路径。 | P1 |
| 一键引用 | 教师可将公开病例引用到自己的病例库，并可基于引用副本进行班级级变量设置。 | P1 |
| 引用计数 | 展示病例被引用次数，用于衡量病例质量和传播度。 | P2 |
| 同行评分 | 教师可对已使用病例进行 1-5 星评分，并填写简短评价。 | P2 |
| 官方认证 | 管理员医学准确性终审通过后，病例展示“官方认证”标识。 | P1 |
| 下架机制 | 管理员可因医学错误、版权问题、敏感内容下架病例。 | P1 |

#### 4.2.3 内容状态流转

`草稿` → `教师提交审核` → `管理员待审` → `审核通过/驳回` → `广场展示` → `被引用` → `更新版本/下架`

#### 4.2.4 验收标准

- 教师提交病例后，管理员待办列表必须出现审核红点。
- 广场列表支持按科室、疾病系统、难度、评分、引用量筛选。
- 引用病例必须生成独立副本，原作者后续修改不影响已下发作业。
- 被下架病例不再允许新引用，但已发布作业保留历史可追溯记录。

### 4.3 教师端：作业分发与防作弊变量

#### 4.3.1 功能目标

支持教师将病例训练任务批量分发给班级，并通过变量机制降低学生互相复制答案的可能性。

#### 4.3.2 功能说明

| 子功能 | 需求说明 | 优先级 |
| --- | --- | --- |
| 作业创建 | 设置作业标题、说明、病例、班级/学生、截止时间、是否允许补交。 | P0 |
| 大病历要求 | 可配置是否要求提交大病历、字数范围、模板要求。 | P0 |
| 防作弊变量 | 支持设置同病不同症、不同检验值、不同患者年龄、不同并发症等随机变量。 | P1 |
| 作业实例生成 | 系统为每名学生生成独立 assignment_instance 和变量快照。 | P0 |
| 进度看板 | 展示未开始、问诊中、已提交、格式打回、AI 批阅中、待教师复核、已完成。 | P0 |
| 催交通知 | 支持对未提交学生发送站内提醒。 | P2 |

#### 4.3.3 防作弊变量规则

- 变量必须由教师预先配置范围，不能由 AI 任意生成医学事实。
- 每个学生作业实例保存变量快照，确保批阅、复核、申诉时可追溯。
- 变量不能改变病例的核心教学目标。例如“急性心梗”病例不能随机成“肺炎”。

### 4.4 教师端：智能批阅与格式盾牌

#### 4.4.1 功能目标

在大病历进入 AI 深度批阅前，先做结构和格式校验，减少无效批阅、节省教师时间与模型成本。

#### 4.4.2 格式盾牌需求

| 校验项 | 规则示例 | 处理方式 |
| --- | --- | --- |
| 必填段落 | 主诉、现病史、既往史、过敏史、体格检查、辅助检查、初步诊断必须存在。 | 不通过则打回 |
| 主诉字数 | 主诉建议 20 字以内，需包含主要症状和持续时间。 | 提示修改 |
| 过敏史 | 不允许空白，未知需写“否认”或“不详”。 | 不通过则打回 |
| 时间线 | 现病史需体现症状发生、发展、就诊经过。 | 提示修改 |
| 禁止粘贴无关内容 | 检测明显模板残留、乱码、重复段落。 | 不通过则打回 |

#### 4.4.3 AI 深度批阅需求

| 批阅维度 | 说明 |
| --- | --- |
| 文书规范 | 错别字、术语不规范、段落缺失、格式不符合大病历要求。 |
| 医学事实 | 检查值解释错误、体征与诊断不匹配、疾病名称错误。 |
| 逻辑链条 | 主诉、现病史、体征、辅助检查、诊断之间是否存在断裂。 |
| 鉴别诊断 | 是否遗漏高危鉴别诊断，是否错误排除重要疾病。 |
| 人文表达 | 是否存在不尊重患者、沟通冷漠、表达不清的问题。 |

#### 4.4.4 人工复核规则

- 教师可以修改 AI 分数、扣分项、评语和错误类型。
- 最终成绩以教师复核结果为准。
- 所有覆盖操作写入 `medical_record_review` 和 `audit_log`。

### 4.5 教师端：学情看板

#### 4.5.1 功能目标

将班级训练行为和 AI 评估结果转化为可行动的教学洞察。

#### 4.5.2 看板指标

| 指标 | 说明 |
| --- | --- |
| 作业完成率 | 按班级、作业、学生维度统计完成情况。 |
| 平均 OSCE 分 | 展示采集、逻辑、沟通、人文四维均分。 |
| 共性漏问项 | 统计全班最常漏问的病史要点和体征。 |
| 共性误诊 | 统计高频错误诊断及其对应病例。 |
| 过度检查 | 统计不必要检查、重复检查和成本超支行为。 |
| 薄弱知识点 | 聚合知识点掌握度，形成课堂补救建议。 |

### 4.6 学生端：多模态 AI 问诊室

#### 4.6.1 功能目标

构建接近真实临床场景的沉浸式问诊训练环境，让学生在低风险环境中练习“问、查、判、写、复盘”。

#### 4.6.2 功能说明

| 子功能 | 需求说明 | 优先级 |
| --- | --- | --- |
| 流式对话 | AI 病人以打字机效果回复，模拟真实交流节奏。 | P0 |
| 病人性格 | 根据病例配置表现为配合、隐瞒、焦虑、暴躁等风格。 | P1 |
| 影像上传 | 支持上传 X 光、CT、检验报告截图，并记录图片 URL。 | P1 |
| 圈画异常点 | 学生可在图片上圈画疑似异常区域，前端记录坐标比例。 | P1 |
| 检查申请 | 学生可申请检查，系统返回预置或 AI 解释后的检查结果。 | P0 |
| 诊断提交 | 学生可提交初步诊断、鉴别诊断和处理建议。 | P0 |
| 引用溯源 | AI 涉及教材知识时展示书名、章节、页码。 | P1 |

#### 4.6.3 多模态约束

- 图片格式支持 JPG、PNG，DICOM 需先转为教学图片后上传。
- 单张图片最大 5MB，单次会话最多上传 5 张。
- 学生圈画坐标使用相对坐标 `(x, y, w, h)`，避免不同屏幕尺寸导致定位偏差。
- AI 读图反馈必须提示“仅用于教学训练，不具备临床诊断效力”。

### 4.7 学生端：临床思维决策树与卫生经济学提示

#### 4.7.1 功能目标

实时可视化学生的诊断推理过程，让学生看到自己问过什么、排除了什么、遗漏了什么，以及检查决策是否符合成本意识。

#### 4.7.2 节点类型

| 节点类型 | 示例 | 状态 |
| --- | --- | --- |
| symptom | 胸痛、咳嗽、腹痛 | 已询问 / 未询问 / 关键遗漏 |
| history | 既往史、过敏史、家族史 | 已采集 / 需追问 |
| exam | 心电图、血常规、胸部 CT | 已开立 / 建议开立 / 过度检查 |
| diagnosis | 肺炎、心梗、肺栓塞 | 待鉴别 / 已排除 / 错误排除 / 高危遗漏 |
| cost | 检查费用、累计费用 | 正常 / 接近上限 / 超支 |

#### 4.7.3 卫生经济学规则

- 每个检查项目需配置参考费用。
- 前端实时展示本次问诊累计检查费用。
- 当学生选择高价检查但未完成低成本必要检查时，系统提示“是否已有足够指征”。
- 超出教师配置的成本阈值时，思维树展示超支提示，但不强制阻止学生继续。

### 4.8 学生端：苏格拉底式反思引导

#### 4.8.1 功能目标

诊断错误时不直接给答案，而是通过逐级提示帮助学生形成自我修正能力。

#### 4.8.2 三级降级策略

| 等级 | 触发条件 | 输出方式 |
| --- | --- | --- |
| 一级：反问启发 | 学生诊断方向偏差但仍有可修正空间 | 用问题引导，如“你是否还需要确认胸痛与活动的关系？” |
| 二级：关键线索 | 学生重复忽略关键证据 | 给出线索，如“心电图 ST 段改变与你的诊断是否一致？” |
| 三级：标准路径 | 学生仍无法修正，或问诊结束进入复盘 | 展示标准路径，并标注学生在哪一步脱轨。 |

#### 4.8.3 约束

- 一级和二级提示不能直接暴露最终诊断。
- 三级提示只在训练结束、教师允许或学生主动查看复盘时展示。
- 所有提示需保留在会话记录中，用于后续错题本和复盘报告。

### 4.9 学生端：OSCE 四维雷达图

#### 4.9.1 功能目标

问诊结束后，从 OSCE 能力视角评价学生表现，帮助学生理解“哪里会、哪里不会、下一步怎么练”。

#### 4.9.2 四维评分

| 维度 | 评分内容 | 示例扣分点 |
| --- | --- | --- |
| 病史采集 | 主诉、现病史、既往史、过敏史、家族史、个人史完整性。 | 未询问胸痛持续时间、未问过敏史。 |
| 诊断逻辑 | 鉴别诊断、检查选择、证据链推理、危险信号识别。 | 胸痛病例未考虑急性冠脉综合征。 |
| 沟通技巧 | 语言清晰、追问自然、解释充分、倾听患者。 | 连续机械提问，无解释与安抚。 |
| 人文关怀 | 尊重患者、关注焦虑、隐私保护、风险告知。 | 对患者担忧无回应。 |

#### 4.9.3 输出内容

- 四维雷达图。
- 每维得分与一句话评价。
- 3 个主要优点。
- 3 个优先改进点。
- 推荐训练病例或教材章节。

### 4.10 学生端：每日一例与学习热力图

#### 4.10.1 功能目标

通过 5 分钟极简病例训练提高学生日活，让平台从“考试前工具”变成“日常训练伴侣”。

#### 4.10.2 每日一例形态

- 一个极简病例摘要。
- 1-2 个关键检查结果。
- 学生选择最可能诊断。
- 学生选择一个必须做和一个应避免的检查。
- 系统即时反馈答案、避坑点和教材出处。

#### 4.10.3 学习热力图

- 首页展示 365 天打卡日历。
- 完成每日一例、完成作业、完成自主病例均可计入学习行为。
- 颜色深浅根据当日有效训练次数或训练时长变化。
- 不鼓励刷量，同一病例重复训练只记一次有效打卡。

### 4.11 学生端：错题本与 AI 复盘报告

#### 4.11.1 功能目标

自动沉淀学生的错误诊断、漏问项、错误检查和文书问题，形成可复习、可导出的成长轨迹。

#### 4.11.2 错题本内容

| 错题类型 | 记录内容 |
| --- | --- |
| 诊断错误 | 学生诊断、标准诊断、关键证据、脱轨节点。 |
| 漏问病史 | 漏问项、为什么重要、对应疾病风险。 |
| 检查错误 | 漏开关键检查、开立过度检查、成本超支原因。 |
| 文书错误 | 大病历中被 AI 或教师标注的问题。 |
| 沟通问题 | 冷漠表达、未安抚患者、未解释检查目的。 |

#### 4.11.3 AI 复盘报告

- 支持按疾病系统、时间范围、错误类型生成报告。
- 报告标题示例：“胸痛问诊中，你漏掉的 3 个关键体征”。
- 支持导出 PDF。
- PDF 内容包含训练概览、典型错题、标准路径、教材页码、下一步训练建议。

### 4.12 学生端：个性化补救路径

#### 4.12.1 功能目标

当系统发现学生连续在某些知识点薄弱时，自动推送更合适的教材段落、微课视频和低难度病例。

#### 4.12.2 推荐规则

- 连续 N 次在同一知识点得分低于 0.6，触发薄弱点。
- 推荐内容需按“教材复习 → 简单病例 → 标准病例 → 综合病例”递进。
- 教材内容必须带书名、章节、页码。
- 学生完成补救病例后，重新计算掌握度。

### 4.13 管理端：全局驾驶舱

#### 4.13.1 功能目标

## 五、核心业务流程

### 5.1 病例创建与发布流程

1. 教师创建病例草稿。
2. 系统校验必填项和医学配置完整性。
3. 教师进入预览试诊。
4. 教师选择发布至个人病例库、班级作业或提交病例广场。
5. 若提交病例广场，进入管理员审核。
6. 管理员审核通过后，病例在广场展示。

### 5.2 问诊训练流程

1. 学生选择病例并进入问诊室。
2. FastAPI 根据病例配置初始化 SP Agent、Mentor Agent、Evaluator Agent。
3. 学生发起问诊，系统通过 SSE 流式返回病人回答。
4. Mentor Agent 增量更新 reasoning_tree。
5. 学生开立检查，系统返回检查结果和费用。
6. 学生提交诊断。
7. 系统根据诊断准确性触发反思引导或进入总结。
8. Evaluator Agent 生成 OSCE 评分、错题、复盘建议。
9. Spring Boot 归档会话数据。

### 5.3 大病历批阅流程

1. 学生提交大病历。
2. Spring Boot 执行格式盾牌校验。
3. 不通过：返回结构化错误，学生修改后重新提交。
4. 通过：进入 AI 批阅队列。
5. FastAPI Reviewer Agent 返回批阅 JSON。
6. Spring Boot 存储批阅结果并通知教师。
7. 教师复核，可覆盖 AI 结果。
8. 最终结果同步给学生，错误项进入错题本。

### 5.4 管理审核流程

1. 管理员查看待办审核列表。
2. 对教师资质、病例内容、敏感内容进行审核。
3. 审核通过或驳回均需填写原因。
4. 系统通知提交人。
5. 审核动作写入 `audit_log`。

## 六、用户故事与验收标准

### 6.1 教师：创建虚拟病人

**User Story**：作为带教老师，我希望通过表单快速创建一个具有主诉、隐藏疾病、性格特点和检查结果的虚拟病人，以便在课堂或课后让学生进行针对性训练。

**验收标准**：

- 必填项包括病例标题、适用年级、主诉、年龄、真实诊断、至少 1 个知识点标签。
- 创建成功后 2 秒内返回 `case_id`。
- 教师可保存草稿、预览试诊、发布作业。
- 学生端不能看到隐藏疾病和标准路径。

### 6.2 教师：引用病例广场病例

**User Story**：作为教师，我希望能预览其他老师分享的病例，并一键引用到我的班级，以便节省备课时间。

**验收标准**：

- 广场病例支持筛选、搜索、排序。
- 引用前可预览试诊。
- 引用后生成独立副本。
- 原病例展示引用次数 +1。

### 6.3 教师：分发防作弊作业

**User Story**：作为教师，我希望为同一个病例设置不同变量，让每名学生拿到略有差异的患者信息，以便减少抄袭。

**验收标准**：

- 教师可配置变量范围。
- 每名学生作业实例生成变量快照。
- AI 批阅使用该学生对应的变量快照作为标准答案。
- 教师可查看每名学生的变量版本。

### 6.4 学生：多模态问诊

**User Story**：作为学生，我希望能上传影像或检验报告并圈出异常点，让 AI 病人和导师反馈我的判断，以便训练影像、检验与临床诊断结合能力。

**验收标准**：

- 支持 JPG/PNG，单张最大 5MB。
- 前端能输出圈选区域相对坐标。
- 图片和圈选信息写入会话记录。
- 多模态回复首轮反馈不超过 3 秒，无法满足时展示友好等待或降级提示。

### 6.5 学生：查看临床思维树

**User Story**：作为学生，我希望问诊过程中实时看到自己的诊断脑图，以便发现漏问、误排除和过度检查。

**验收标准**：

- 接收 `event: tree` 后，前端 200ms 内完成增量渲染。
- 节点最多展示 50 个，超过后折叠历史节点。
- 检查费用实时累计。
- 高危遗漏节点需醒目标识。

### 6.6 学生：错题复盘

**User Story**：作为学生，我希望系统自动整理我被纠错过的诊断和漏项，以便考前按疾病系统复习。

**验收标准**：

- 问诊结束后自动生成错题记录。
- 错题支持按疾病系统、错误类型、时间筛选。
- 支持生成 PDF 复盘报告。
- 报告包含教材页码溯源。

### 6.7 管理员：审核病例内容

**User Story**：作为管理员，我希望审核教师提交到病例广场的病例，以便保障医学准确性和内容安全。

**验收标准**：

- 管理端显示待审核病例列表和红点提醒。
- 管理员可查看隐藏诊断、标准路径、试诊效果。
- 审核通过后病例出现官方认证标识。
- 审核驳回需填写原因，并通知提交教师。

### 6.8 运维：模型降级

**User Story**：作为运维工程师，我希望在大模型超时或限流时一键切换备用模型或降级策略，以便保障学生训练不中断或不白屏。

**验收标准**：

- 可配置主模型、备用模型、超时时间、重试次数。
- 模型异常时前端展示友好提示，不出现 5xx 白屏。
- 降级事件写入日志并在驾驶舱展示。

## 七、系统架构与技术方案

### 7.1 总体架构

系统采用异构服务架构：

- **Flutter 移动端（学生/教师）**：负责学生问诊、教师病例配置/批阅等核心教学功能。一套代码同时支持 Android 和 iOS；学生与教师共用**同一 App 包**，登录后按 JWT 中的 `role` 分流到各自首页，应用商店只发布一个统一包。
- **Vue 3 Web 管理端（教学秘书/教研室主任/管理员/运维）**：负责全局驾驶舱、用户管理、内容审核、系统配置、审计日志。PC 浏览器访问；App 不开放管理类功能。
- **Spring Boot 业务中台**：负责鉴权、用户、班级、病例、作业、批阅、审计、配置、文件网关。
- **FastAPI AI 中台**：负责大模型调度、LangGraph 智能体编排、RAG、Embedding、SSE 流式输出。
- **MySQL**：存储业务数据、权限、作业、会话、评分、审计。
- **Milvus**：存储教材切片向量和知识资源向量。
- **对象存储 / 本地文件服务**：存储教材 PDF、影像图片、复盘 PDF。

#### 7.1.1 Flutter 技术栈选型

| 类别 | 技术方案 | 说明 |
| --- | --- | --- |
| 状态管理 | Riverpod 2.x | 编译时安全、支持异步、适合复杂业务逻辑 |
| 路由 | go_router | 声明式路由、支持深链接、角色守卫 |
| 网络请求 | dio | 支持拦截器、取消请求、文件上传、SSE 流式 |
| UI 组件 | Material Design 3 | Google 官方设计规范，支持动态主题 |
| 图表 | fl_chart | 轻量级、支持雷达图、折线图、柱状图 |
| 本地存储 | shared_preferences + hive | 轻量配置 + 结构化数据离线缓存 |
| 图片处理 | image_picker + image_cropper | 相机/相册选取、裁剪、压缩 |
| PDF 生成 | pdf + printing | 生成和分享复盘报告 PDF |

### 7.2 AI 智能体分工

| Agent | 职责 |
| --- | --- |
| SP Agent | 扮演虚拟病人，根据病例配置回答学生问诊。 |
| Mentor Agent | 维护思维树，识别漏问、错误排除、高危遗漏，触发苏格拉底提示。 |
| Vision Agent | 处理影像/检验图片和圈选区域。 |

### 7.3 RAG 知识库

#### 7.3.1 教材处理

1. 管理员上传教材 PDF。
2. Spring Boot 保存文件并创建教材版本记录。
3. FastAPI 解析 PDF，按章节和页码切块。
4. 每个 chunk 存储 `book_name`、`edition`、`chapter`、`page_number`、`chunk_text`。
5. Embedding 后写入 Milvus。

#### 7.3.2 溯源要求

- AI 输出涉及教材知识时，必须返回引用来源。
- 前端展示书名、版本、章节、页码。
- 若无可信来源，AI 应提示“未在当前教材库中找到明确依据”，避免编造出处。

## 九、API 契约

### 9.1 Spring Boot 面向前端接口

> **移动端（Flutter）**：通过 dio 发起 HTTP 请求，JWT 存储在 flutter_secure_storage 中。
> **Web 管理端（Vue 3）**：通过 axios 发起 HTTP 请求，JWT 存储在 httpOnly Cookie 或 localStorage 中。

**登录与登录后置校验（`/api/v1/auth/login`）**

- 登录成功返回 JWT，Payload 含 `user_id`、`role`、`audit_status`（仅教师有意义）。
- 学生（role=0）：登录即可使用全部学生功能，无后置校验。
- 教师（role=1）：登录后按 `audit_status` 分流：
  - `2 通过`：正常进入教师首页。
  - `0 未提交`：进入教师首页但仅可预览试诊、浏览病例广场，所有"创建/发布/批阅"入口置灰并提示"请先完成教师资质认证"，提供去认证入口。
  - `1 待审核`：进入教师首页，功能同未提交，提示"资质审核中，预计 X 个工作日"。
  - `3 驳回`：进入教师首页，功能同未提交，提示驳回原因并提供重新提交入口。
- 教学秘书/教研室主任/管理员/运维：走 Web 管理端登录，App 端拒绝该类 role 登录并提示"请使用 Web 管理端"。

## 十、非功能性需求

### 10.1 性能

| 场景 | 指标 |
| --- | --- |
| 纯文本问诊 | P95 首 Token < 1 秒，P95 完整首轮回复 < 5 秒 |
| 多模态问诊 | P95 首 Token ≤ 1.5 秒，P95 首轮反馈 < 3 秒 |
| 单班级并发 | 单班级 50 人同时建立 SSE 无排队 |
| 思维树渲染 | 接收增量事件后 200ms 内完成前端更新 |
| 大病历批阅 | 单份 5000 字以内病历异步批阅 P95 < 15 秒 |
| 管理驾驶舱 | 首页核心指标 P95 3 秒内加载完成 |

### 10.2 可用性与容灾

- 核心业务可用性目标不低于 99.9%，统计周期按月。
- AI 服务不可用时，系统必须自动降级到规则引擎或静态提示，不允许白屏。
- 生产环境必须支持健康检查、实例滚动更新、快速回滚和灰度发布。
- 关键业务数据按日备份，恢复演练至少每季度一次。
- RTO 不高于 30 分钟，RPO 不高于 15 分钟。

### 10.3 安全

- `/api/admin/*` 必须独立鉴权，且校验管理员/运维角色。
- 教师只能访问授权班级和自己创建/引用的病例。
- 学生只能访问本人作业、会话、错题和报告。
- 统一采用 RBAC + 数据权限双层控制。
- 管理端支持关键操作二次确认和高危操作审计。
- 敏感字段脱敏展示，如手机号、证件号。
- 文件上传需校验类型、大小和安全扫描结果。
- 所有 JWT 必须设置过期时间和刷新策略。

### 10.4 隐私与合规

- 页面底部固定医学免责声明：“系统提供内容仅供医学思维训练，不具备真实临床诊疗效力。”
- 学生训练数据仅用于教学评估，未经授权不得导出用于研究。
- 导出成绩、报告、学情数据需写入审计日志。
- 需要支持数据最小化、访问留痕、导出审批和脱敏展示。
- 真实患者信息不得作为训练内容进入系统。
- AI 不得回答真实患者诊疗建议、药物处方、违法制毒、自伤他伤等越界内容。

### 10.5 可观测性

- 所有模型调用记录 `session_id`、`user_id`、`case_id`、`model_name`、`token_cost`、`latency`、`status`。
- 所有 SSE 异常需记录断开原因。
- 管理端展示 Token 消耗趋势和异常调用。
- 支持按会话追踪一次问诊中的 Spring Boot、FastAPI、模型调用链路。

### 10.6 兼容性

- Android：最低支持 Android 6.0（API 23），推荐 Android 10+（API 29）。
- iOS：最低支持 iOS 13.0，推荐 iOS 15+。
- 屏幕适配：支持 4.7 寸至 12.9 寸屏幕，响应式布局。
- 网络：支持弱网环境下的离线缓存和断点续传。

### 10.7 发布与运维

- 生产发布必须支持灰度、回滚和版本冻结。
- 核心变更必须有变更单和审批记录。
- 线上问题必须可通过审计日志、链路追踪和指标面板定位。
- 重要配置变更必须支持操作人、时间、前后值追溯。

## 十二、风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| AI 医学回答不准确 | 误导学生学习 | 强制 RAG 溯源、医学专家审核病例、AI 输出免责声明、教师最终复核。 |
| 模型成本不可控 | 运营费用超预算 | Token 预算、每日阈值、超额预警、批阅队列限流、缓存常用教材召回。 |
| 教师不信任 AI 批阅 | 使用率低 | 保留人工复核与覆盖机制，展示 AI 扣分依据，支持申诉。 |
| 病例广场内容质量参差 | 影响教学可信度 | 管理员终审、官方认证、评分机制、下架机制。 |
| 学生刷每日一例 | 数据失真 | 重复病例不重复计有效打卡，统计正确率和耗时而非只统计次数。 |
| 并发 SSE 不稳定 | 问诊体验差 | 压测、连接池配置、超时重连、模型降级、前端断线恢复。 |
| 隐私数据泄露 | 合规风险 | 权限隔离、脱敏展示、审计日志、导出审批。 |

## 十三、里程碑建议

### 13.1 Phase 1：企业级底座与核心闭环

目标：先建立可持续演进的生产底座，同时跑通核心教学闭环。

范围：

- 统一登录、RBAC、数据权限、审计日志。
- Spring Boot 业务中台、FastAPI AI 中台、MySQL、Milvus、对象存储基础能力。
- SP 零代码配置、作业分发、AI 问诊 SSE、OSCE 四维评分。
- 大病历格式盾牌、AI 批阅、教师复核、基础学情看板。
- 监控告警、链路追踪、模型调用日志、基础成本统计。

交付标准：

- 核心链路端到端自动化测试通过。
- P0 接口完成字段级契约、错误码和鉴权规则。
- 生产环境具备灰度、回滚、备份和健康检查能力。

### 13.2 Phase 2：完整教学产品能力

目标：补齐学生增长、教师复用和学习复盘能力，形成完整产品体验。

范围：

- 病例广场、官方认证、同行评分、引用副本。
- 每日一例、学习热力图、错题本、AI 复盘 PDF。
- 临床思维决策树、卫生经济学提示、苏格拉底式反思。
- 个性化补救路径、教材页码溯源、推荐训练病例。

交付标准：

- 教师、学生、管理端三类用户均可完成完整任务流。
- 内容审核、下架、申诉和版本追溯流程可用。
- 学习数据与学情看板指标口径一致。

### 13.3 Phase 3：治理、安全与规模化运营

目标：支撑学院级真实使用和长期运营。

范围：

- 全局驾驶舱、教师资质审核、内容风控、教材版本管理。
- 模型容灾、多供应商适配、Token 预算、成本预警。
- 数据导出审批、敏感操作审计、运维配置中心。
- 压测、容灾演练、安全扫描、发布审批和运行手册。

交付标准：

- 满足 10 章非功能性需求。
- 完成安全测试、性能测试、稳定性测试和恢复演练。
- 形成上线检查清单、应急预案和运维交接文档。

### 13.4 Phase 4：试点上线与持续优化

目标：在真实教学场景灰度上线，基于数据持续优化产品和模型。

范围：

- 选择 1-2 个试点班级进行灰度上线。
- 建立教师反馈、学生反馈、AI 质量抽检和运营周报机制。
- 按周复盘活跃、批阅效率、模型成本、错误率和内容质量。
- 根据试点结果调整病例模板、评分规则、推荐策略和容量配置。

### 13.5 App 发布与上架流程

> 独立于业务迭代，贯穿各 Phase 的工程化流程。

**上架策略**：应用商店只发布**一个统一 App 包**，学生与教师共用，角色由登录态（JWT `role`）决定，不拆分学生版/教师版，避免双包维护与审核成本。

| 阶段 | 关键事项 |
| --- | --- |
| 上架准备 | 准备应用名称、图标、截图、隐私政策、用户协议、医学免责声明；归类"教育/医学教育"，规避"医疗诊断"。 |
| 内测 | TestFlight（iOS）+ 内测分发（Android）下发试点班级，收集崩溃与性能数据。 |
| 商店审核 | 提交 App Store / Google Play，备齐医学内容合规说明与教学授权材料，预留 1-2 周审核周期。 |
| 灰度发布 | 按学院/班级分批开放，监控崩溃率、SSE 稳定性、Token 成本，异常超阈值自动暂停灰度。 |
| 全量上线 | 灰度指标达标后全量推送；保留强制更新能力用于修复重大缺陷。 |
| 热更新 | 上线后通过管理端发布签名补丁，客户端校验后应用，失败自动回滚。 |
| 版本退役 | 旧版本在强制更新公告 30 天后停止服务端支持，引导用户升级。 |

## 十五、质量门禁与上线检查清单

### 15.1 需求门禁

- 所有 P0 / P1 需求必须具备用户故事、业务规则、权限规则、异常路径和验收标准。
- 涉及 AI 输出的功能必须定义输入、输出、评分依据、溯源要求和人工复核规则。
- 涉及数据导出、审核、下架、评分覆盖的功能必须定义审计字段和追溯口径。
- 需求变更必须记录变更原因、影响范围、优先级和验收人。

### 15.2 设计门禁

- 核心链路必须产出流程图、状态机、接口契约和数据模型。
- 移动端、Web 管理端、后端、AI 中台之间的职责边界必须清晰。
- 所有异步任务必须定义任务状态、失败重试、幂等策略和人工补偿方案。
- 所有高危操作必须具备二次确认、权限校验和审计记录。

### 15.3 测试门禁

- 单元测试覆盖核心业务规则、权限判断、数据状态流转和异常分支。
- 集成测试覆盖登录、病例创建、作业分发、问诊、批阅、复核、学情看板、审计日志。
- 性能测试覆盖 50 人并发 SSE、批阅队列、驾驶舱查询和文件上传。
- 安全测试覆盖越权、注入、文件上传、敏感信息泄露、JWT 过期和刷新。
- AI 质量测试覆盖医学准确性、RAG 溯源、拒答边界、幻觉率和评分一致性。

### 15.4 发布门禁

- 发布前必须完成数据库迁移脚本、回滚脚本、配置差异检查和依赖版本锁定。
- 发布必须经过开发环境、测试环境、预生产环境、生产灰度环境。
- 灰度期间必须监控错误率、延迟、SSE 断开率、Token 成本和用户反馈。
- 若出现 P0 故障、数据错乱、权限越权或 AI 越界输出，必须立即回滚并冻结发布。

### 15.5 运营门禁

- 上线前必须准备管理员手册、教师使用手册、学生使用说明和运维应急预案。
- 试点期必须建立周报机制，跟踪活跃、完成率、批阅效率、模型成本和内容质量。
- 医学专家需要定期抽检病例、AI 批阅样本和复盘报告。
- 用户反馈必须进入缺陷池或需求池，并标注优先级、责任人和处理时限。

- 接口路径：`/api/v1/{模块}/{资源}`，如 `/api/v1/teacher/cases`。
- 响应格式统一使用 `R<T>`：

```json
{
  "code": 0,
  "message": "success",
  "data": { }
}
```

- 分页响应使用 `PageResult<T>`：

```json
{
  "code": 0,
  "data": {
    "list": [],
    "total": 100,
    "page": 1,
    "pageSize": 20
  }
}
```

- 错误码规范：`0` 成功，`1xxx` 客户端错误，`5xxx` 服务端错误。

#### 16.3.4 代码风格

- 使用 Lombok 简化样板代码（`@Data`、`@Builder`、`@Slf4j`）。
- Service 层禁止直接操作 `HttpServletRequest/Response`。
- 事务注解 `@Transactional` 只加在 Service 层。
- 禁止在 Controller 层写业务逻辑。
- 所有数据库查询必须使用 MyBatis Plus 的 LambdaQueryWrapper，禁止拼接 SQL。
- 敏感操作（删除、修改角色、审核）必须记录审计日志。

#### 16.4.3 代码风格

- 涉及医学知识的 Agent 输出必须附带 RAG 溯源，无溯源时明确提示。

### 16.5 通用规范

#### 16.5.1 Git 提交规范

提交信息格式：`<type>(<scope>): <subject>`

| type | 说明 |
| --- | --- |
| feat | 新功能 |
| fix | 修复 Bug |
| refactor | 重构（不改变功能） |
| style | 代码格式调整 |
| docs | 文档更新 |
| test | 测试相关 |
| chore | 构建、依赖、工具 |

示例：`feat(student): 实现问诊室 SSE 流式对话`

#### 16.5.2 API 版本管理

- 所有接口必须带版本号前缀：`/api/v1/`。
- 不兼容的变更必须升级版本号（v1 → v2）。
- 旧版本接口保留至少 3 个月过渡期。

#### 16.5.3 错误处理

- 前端：所有 API 请求必须 try-catch，展示用户友好的错误提示，禁止白屏或控制台报错。
- 后端：全局异常处理器捕获所有异常，返回统一格式 `R<T>`。
- AI 中台：LLM 超时/限流时返回降级文案，禁止暴露原始错误信息。

#### 16.5.4 安全规范

- JWT 存储：Flutter 使用 `flutter_secure_storage`（Keychain/Keystore）。
- 敏感接口必须校验角色权限，禁止前端判断代替后端校验。
- 文件上传：校验类型、大小、扩展名，禁止直接存储用户文件名。
- 所有用户输入必须经过校验和转义，防止注入攻击。
