# 问诊读图降级排查手册

> 适用症状：移动端问诊室发图后，患者气泡显示 **「[读图服务降级] 读图服务暂不可用，请稍后重试。」**
> 最后整理：2026-09-11

---

## 一、先认清一个事实：文案能定位到层

读图链路上不同层失败，会返回**不同**的用户可见文案。看到哪句就知道卡在哪一层：

| 用户看到 | 产生位置 | 含义 |
|---------|---------|------|
| `[读图服务降级] 读图服务暂不可用，请稍后重试。` | **Java 后端** `StudentSessionServiceImpl:400` | `AiPlatformClient.analyzeVision()` 返回 **null** —— 后端根本没拿到可用响应 |
| `[读图服务降级] 【降级模式】当前未配置多模态大模型 API Key…` | AI 中台 `api/vision.py` | AI 侧 `settings.vision_configured == false` |
| `[读图服务降级] 读图失败：XxxError。请稍后重试…` | AI 中台 `api/vision.py` | **模型调用阶段**抛了 `APIError`（Key 错 / 模型名错 / 图片抓不到 / 超时） |
| 无气泡，只有左滑提示「暂未从影像中读到信息」 | 移动端 `chat_room_screen.dart` | 后端返回 200 但响应里没有 `finding` 字段 |
| 完全没有反应 | 移动端 | 请求没发出去（死代码 / 未登录 / 会话未就绪） |

**「读图服务暂不可用」= 后端 analyzeVision 返回 null**，这是排查的起点。

---

## 二、后端返回 null 的全部原因（`AiHttpClient.postDataWithBearer`）

1. `postWithBearer` 抛 `RestClientException` —— **AI 返回非 2xx**，或网络不通。
   日志：`ERROR 调用AI中台失败: POST http://ai:8000/v1/ai/vision/analyze error=...`
2. AI 返回**错误信封**（顶层含 `code`），被判定为失败。
   日志：`WARN AI中台(Bearer)响应中无data字段: ... resp=...`
3. 响应体是空对象 / 解析失败。

> ⚠️ 历史坑（2026-09-11 已修）：`/v1/ai/vision/analyze` 按契约返回**裸 `VisionAnalysisResult`**（无 `{code,data}` 信封）。
> 旧实现「无 `data` 就 return null」把成功的读图结果整包丢弃 → 稳定降级。修复后裸对象原样透传。
> **若日志出现 `无data字段`，说明线上后端仍是旧镜像。**

---

## 三、判定树

```
看到「读图服务暂不可用」
├─ 后端日志有 WARN "无data字段"
│   └─ ⇒ 线上 backend 是旧镜像：部署没落地 / CI 未跑完 / 部署窗口内测试。等 CI 绿或重跑部署
└─ 后端日志有 ERROR "调用AI中台失败: ... error=XYZ"
    ├─ 401 ⇒ JWT_SECRET 不一致，或 App 没带 Authorization（AI 的 require_mobile_student 拒绝）
    ├─ 403 ⇒ AI 侧 session_context 判定「会话不存在/已结束/不属于当前学生」
    ├─ 422 ⇒ validate_image_url 拒绝（地址非 HTTP(S) / 内网地址 / 白名单协议不匹配）
    └─ 500 ⇒ AI 内部异常，看 zhiyu-ai 日志里最后一个 traceback
```

## 三・A、2026-09-11 生产实录（401 定案过程）

**现象**：v1.0.2 APK 上问诊发图 → 患者气泡「[读图服务降级] 读图服务暂不可用，请稍后重试。」；AI 学伴读图正常。

**服务端证据**：

```
HEAD = 7d72cff（最新提交，部署已落地）
zhiyu-backend StartedAt=2026-09-11T05:22:11Z
zhiyu-ai      StartedAt=2026-09-11T05:22:17Z

zhiyu-backend 日志：
2026-09-11 05:45:00 ERROR AiHttpClient - 调用AI中台失败: POST http://ai:8000/v1/ai/vision/analyze error=401 Unauthorized: [no body]  （共 4 次）

zhiyu-ai 日志：
INFO: 172.19.0.8 - "POST /v1/ai/vision/analyze HTTP/1.1" 401 Unauthorized  （共 4 次）
```

**关键判读**：
- `无data字段` 告警**完全没有出现** ⇒ 线上后端已是新代码（丢弃裸对象的旧逻辑已不在）⇒ **本次不是「部署没落地」**。
- 真正的病灶是 **AI 侧 401**，发生在 `require_mobile_student` 依赖上。

### 为什么「学伴能读图、问诊不能」

`require_mobile_student`（移动端 JWT 鉴权）**只被三个端点使用**：

| 端点 | 移动端是否直连 | 后端实际走的路径 | 结果 |
|------|--------------|----------------|------|
| `/v1/ai/chat/stream` | 否 | `/internal/chat/stream` + `X-Internal-Token` | ✅ 正常 |
| `/v1/ai/companion/stream` | 否 | `/internal/companion/stream` + `X-Internal-Token` | ✅ 学伴正常 |
| `/v1/ai/vision/analyze` | **是**（后端直接转发移动端 JWT） | 无内部端点 | ❌ 401 |

⇒ **读图是全链路里唯一把「移动端 JWT」当后端→AI 鉴权凭据的端点**，正是这条跨系统耦合断掉了。

### 两条 401 的区分（AI 侧 detail 不同）

| AI 返回的 detail | 含义 | 方向 |
|---|---|---|
| `缺少登录凭证` | **Authorization 头没到** AI | 后端转发链路 / 客户端未带头 |
| `登录凭证无效或已过期` | 头到了但**验签失败** | `JWT_SECRET` 在 backend 与 ai 之间不一致 |

无头/坏 token 两种情况的 **HTTP 状态码都是 401**，所以必须看 detail 或对比密钥指纹。

### 密钥指纹对比（不泄露密钥明文）

```bash
cd /opt/zhiyu-new
for c in zhiyu-backend zhiyu-ai; do
  printf '%-16s %s\n' "$c" "$(docker exec $c printenv JWT_SECRET | tr -d '\n' | md5sum | cut -d' ' -f1)"
done
printf '%-16s %s\n' "server .env" "$(grep -m1 '^JWT_SECRET=' .env | sed 's/^JWT_SECRET=//' | tr -d '\n' | md5sum | cut -d' ' -f1)"
```

判读：三行 md5 全同 ⇒ 密钥没问题，方向转向「请求头是否真的带上了」；前两行不同 ⇒ **根因就是密钥不一致**。

> ⚠️ 仓库里的 `deploy/release/.env` **不是线上那份**（实测：用它的 `AI_INTERNAL_TOKEN` 打生产 `/ai/internal/config/status` → `401 内部接口鉴权失败`），因此不能拿仓库值反推线上密钥。

## 五、分项自检（不依赖线上日志）

### 5.1 AI 侧白名单是否放行（**生产专属**，dev 跳过白名单）

容器内跑探针，把 env 切成 prod 语义：

```python
from app.core.config import settings
settings.env = "prod"
settings.vision_allowed_hosts = ['http://8.160.161.158']
from app.core.vision_guard import validate_image_url
print(validate_image_url("http://8.160.161.158/uploads/covers/xxx.jpg"))
```

- 裸主机名条目 → **仅允许 https**；要放行 HTTP 必须写 `http://host`。
- 生产 `.env`：`VISION_ALLOWED_HOSTS=["http://8.160.161.158"]`（JSON 数组格式）。

### 5.2 第三方 VLM 能不能抓到你的图

**图片是阿里云/第三方去抓的，不是 AI 容器抓的。** 所以必须验证：
① 图片 URL 公网可达（`curl -sI <url>` 应 200 且 `content-type: image/*`）；
② 第三方能抓（直调模型带该 URL，看是否 `finish=stop`）。

实测参考：`http://8.160.161.158/uploads/covers/cover_*.jpg` 可被 qwen3-omni-flash 正常读取。

### 5.3 移动端是否真的把图发出去了

发送路径必须是 `_onSend()` 分发（有图转 `_sendImage()`）。若「只选图不打字点发送毫无反应」，说明送按钮还绑在 `_sendMessage` 上（旧包缺陷）。

### 5.4 相对路径必须拼绝对地址

后端 `UPLOAD_BASE_URL=/uploads` → 上传接口返回 `/uploads/multimodal/img_xxx.png`。
移动端必须经 `resolveMediaUrl()` 拼成 `http://<API_BASE_URL>/uploads/...`，AI 的 `validate_image_url` 只接受 HTTP(S) 绝对地址。

## 六、易踩的部署坑

- **`deploy.yml` 无 `paths-ignore`**：只改 `docs/` 或 `mobile/` 的提交同样会触发**全量镜像构建 + 服务器 `--force-recreate`**（约 30 分钟）。
  连续两次 push = 两次全量部署；在部署窗口内测试会撞上容器重建。
  建议加：
  ```yaml
  on:
    push:
      branches: [main]
      paths-ignore: ['mobile/**', 'docs/**', '**/*.md']
  ```
- 镜像 tag 固定 `:latest`，**没有版本号端点可查**，只能靠 `git log -1` + `docker inspect .State.StartedAt`。
- 生产演示账号 `student01` / `teacher01` / `admin01` 由 `ProdSecurityInitializer` **有意冻结**（密码仍为 `123456` 时置 `status=1`），无法用来做接口级验证。

## 七、根治方案：读图改走内部 token（**2026-09-11 已实施**）

**问题本质**：后端在同一个 AI 中台里用了两套鉴权（`X-Internal-Token` 与移动端 JWT），
后者把「移动端凭证」跨系统传递，一旦密钥漂移 / header 丢失 / token 过期，
症状只表现为一句「读图服务暂不可用」，排查成本极高。

### 已落地的改动

| 文件 | 改动 |
|------|------|
| `ai/app/api/vision.py` | 抽出 `_run_vision_analyze(req, student_id)`；新增 `POST /internal/vision/analyze`（`require_internal_token`，`student_id` 取请求体）；原 `/v1/ai/vision/analyze` 保留（只认 JWT） |
| `ai/app/models/chat.py` | `VisionAnalyzeRequest` 增加 `student_id`（仅内部端点使用） |
| `backend/…/AiPlatformClient.java` | `analyzeVision(...)` 去掉 `mobileToken`，改调 `/internal/vision/analyze` |
| `backend/…/AiHttpClient.java` | 新增 `postDataInternal()`（内部 token + 容忍裸业务对象）；抽出 `parseDataOrBare()`；**HTTP 错误时显式打印状态码与 AI 响应体**，未携带 Authorization 头时告警 |
| `backend/…/StudentSessionController.java`<br>`StudentSessionService(.Impl).java` | 不再读取/透传 `Authorization`，签名去掉 `mobileToken` |
| `ai/tests/contract/test_api_contracts.py` | 新增 4 例：内部端点缺 token 401、缺 `student_id` 422、正常 200、公网端点忽略 body 里的 `student_id` |

**安全性未放松**：学生身份仍由后端 JWT 过滤器注入 `UserContext` 校验一次，
AI 侧 `backend_client.session_context()` 再校验一次会话归属 —— 与
`/internal/chat/stream`、`/internal/companion/stream` 完全一致。

### 本地验证结果（2026-09-11）

- `pytest tests/unit tests/contract tests/security tests/e2e -q` → **117 passed, 4 skipped**
- 后端 `mvn clean package -DskipTests` 通过
- 端到端：`POST /api/v1/student/sessions/107/image/analyze` →
  日志 `POST http://ai:8000/internal/vision/analyze bodyKeys=[image_url, session_id, student_id, student_note]`
  → `200 OK` → `返回裸业务对象，按原样透传` → **移动端拿到真实读图结论**（非降级文案）
- 越权回归：用 student01 的 token 读他人会话 106 → `code=1003 问诊会话不属于当前学生` ✅

### 遗留观察点

生产两个容器的 `JWT_SECRET` 指纹相同（`32ee5faa…`），但**与服务器 `.env` 文件的值不同**（文件为 `e980d2cd…`），
说明 `.env` 被修改过或未被 compose 采用。本次改动已不再依赖该密钥，但下次部署后请留意新日志，
它会直接给出「未携带 Authorization 头」或「HTTP 401 body=…」的明确结论。

## 八、⚠️ 安全告警（2026-09-11 发现）

`deploy/release/.env` 把**生产密钥明文提交进了仓库**：`MYSQL_ROOT_PASSWORD`、
`REDIS_PASSWORD`、`JWT_SECRET`、`AI_INTERNAL_TOKEN`、`OPS_TOKEN`、
`VISION_API_KEY` / `LLM_API_KEY` / `DASHSCOPE_API_KEY` / `SILICONFLOW_API_KEY`。

即使仓库私有，也建议：① **轮换全部密钥**；② 从仓库移除该文件（`.gitignore`）+
清理历史；③ 生产 env 只保留在服务器 `/opt/zhiyu-new/.env`，或改用 GitHub Secrets
在部署时注入。
